# Маршрут к доказательству

> Живая методика точной навигации по коду и ограниченного чтения контекста.
>
> **Статус:** переносимый локальный developer workflow. Это не production-
> стандарт, не автоматический root-cause анализ и не система самообучения.

## Зачем этот документ

Этот документ — единое место, где описана методика: как из инженерного вопроса
прийти к проверяемому факту, не загружая репозиторий целиком и не подменяя
доказательство похожими фрагментами. Его надо дополнять датированными разделами
или ссылками на новые эксперименты, а не молча переписывать старые выводы.

Методика переносима: имена проектов, каталоги, сервисы, ключи и реальные
инциденты намеренно не входят в текст. При переносе меняются адаптеры и карты
владения, но не базовые границы метода.

## 1. Проблема: шум вместо доказательства

Открыть весь репозиторий, все похожие документы и старые заметки кажется
надёжным решением. На практике это часто создаёт смесь из актуального кода,
архивных решений, черновиков и соседних компонентов. Чем шире контекст, тем
проще принять совпадение по словам за доказательство.

Главная ошибка проста: **найденное не равно доказанному**. Поисковая карточка,
высокий score, похожий файл или краткий summary могут подсказать направление,
но не подтверждают факт. Доказательство начинается, когда прочитан конкретный
владелец: диапазон исходника, символ, контрактный якорь или сфокусированный
тест.

Широкое чтение создаёт четыре риска:

- **шум** — в вывод попадают несвязанные слои;
- **устаревание** — история выдаётся за текущий код или конфигурацию;
- **ложная похожесть** — соседний файл принимается за владельца поведения;
- **дорогой контекст** — внимание расходуется на материал, который не меняет
  решение.

Цель методики — не запретить поиск, память или summaries. У каждого из них есть
роль: поиск сужает область, история напоминает решения, карточка предлагает
кандидата. Но только выбранный и прочитанный источник может стать опорой для
вывода.

## 2. Контракт доказательств

У каждого вида материала свой вес. Полезно явно держать следующую лестницу:

1. **Кандидатная карточка.** Поисковый результат, score, краткое описание.
   Это направление, а не доказательство.
2. **Выбранный source span.** Точный диапазон строк, символ или договорный
   якорь. Здесь появляется проверяемая опора.
3. **Focused test.** Для утверждения о текущем коде нужен узкий тест, который
   проверяет именно заявленное свойство.
4. **Историческая память.** Помогает вспомнить решения и инциденты, но не
   доказывает нынешние код, конфигурацию или состояние.
5. **Свежий production proof.** Нужен только для утверждений о работающем
   production-контуре; локальные документы и старые логи его не заменяют.

Из этого следует порядок работы:

```text
candidate → selected source → focused test/contract → вывод
                                      ↓
                         live proof, если вопрос о production
```

Если неизвестны проект, владелец или тип нужного доказательства, метод не
компенсирует это поиском «везде». Он останавливается и требует уточнения.

## 3. Как метод появился экспериментально

Метод не был взят готовым. Его собрали после нескольких локальных проверок.
Все числа в этой главе — результаты конкретной исследовательской среды; они не
являются универсальными порогами.

### Широкие карточки

Сначала проверялись полнотекстовые карточки, карточки исходников и добавочный
контекст заголовков. Они помогали ориентироваться, но не показали устойчивого
качества верхней выдачи: в одной слепой проверке базовый и карточный путь дали
одинаковые H@1/H@3 `0,300` и MRR `0,325`; в другой Recall@8 вырос, но H@1 и
MRR ухудшились. Урок: карточки остаются навигацией, а не evidence.

### Свободный естественный язык

Потом проверялся выбор цели по свободному вопросу. Кандидат находился в 19 из
22 случаев, а полный строгий путь — в 16 из 22. Это полезно для человека,
которому нужно сузить поиск, но недостаточно для автопилота.

### Явная цель и строгий gate

Когда цель задавалась точно, результат стал существенно надёжнее: 26 из 26
валидных целей прошли, 2 из 2 невалидных были отклонены. Длинные фрагменты
останавливались на лимите вместо ложного сообщения о полном чтении.

### Диагностический владелец

Следующий эксперимент использовал точный diagnostic code как вход. Результат:
9 из 9 подтверждённых владельцев найдены точно, 21 из 21 неоднозначных или
неподходящих случаев завершились воздержанием, ложных выборов и ложных отказов
не было. Этот результат доказывает качество узкой навигации к проверке, но не
доказывает runtime-причину пользовательского исхода.

### Урок

Эксперименты дали не «умный поиск по всему», а дисциплину:

```text
свободный вопрос → кандидат
точная цель      → строгий маршрут
прочитанный span → доказательство или честная остановка
```

## 4. Сначала выбрать цель, потом читать

Перед чтением фиксируются:

```text
project_id
вопрос
тип доказательства
definition_of_done
do_not_open
context budget
```

После этого выбирается ровно один основной маршрут:

| Маршрут | Когда использовать | Что возвращает |
|---|---|---|
| `stage` | известен этап процесса | владелец этапа и его source/test |
| `symbol` | известна функция, класс, метод | точный AST-символ |
| `diagnostic` | есть машинный код проверки | владелец diagnostic signal |
| `docs` | нужен контракт или правило | точный documentation anchor |

Навигация должна вернуть `target_spec`: тип цели, её имя и владельца. Например:

```json
{
  "target_kind": "symbol",
  "target": "validate_payload",
  "target_owner": "relative/path/to/source.py"
}
```

Это мост между «нашёл похожее место» и «можно открыть конкретный доказательный
фрагмент». Широкий путь или папка остаются навигационными ID, но не проходят как
evidence.

## 5. STOP-2: конверт контекста

STOP-2 задаёт небольшой начальный конверт чтения:

```text
candidate cards: до 5
selected primary sources: до 2
initial excerpt: до 80 строк / до 8000 символов суммарно
linked expansion: до 1, только по новому основанию
full files by default: 0
```

Это стартовые гипотезы, а не вечные константы. В новом репозитории их нельзя
подкручивать под уже увиденный набор оценок: сначала нужен отдельный benchmark.

Особенно важна честная граница. Если символ длиннее бюджета, система показывает
**фактически** прочитанный диапазон и возвращает `context_budget_reached`.
Она не имеет права сообщить `definition_of_done`, если хвост символа не был
прочитан.

```text
точная цель
  → максимум два выбранных источника
  → фактические строки и символы в trace
  → доказано / частично прочитано / нет кандидата
```

`context_budget_reached` — не ошибка. Это сигнал выбрать следующий связанный
контракт, потребителя или тест, а не открыть всё подряд.

## 6. Диагностический код как ключ

Если есть точный код ошибки, можно искать не «почему всё сломалось», а узкого
владельца этого сигнала. Маршрут выглядит так:

```text
diagnostic code → AST literal → enclosing symbol → strict target → bounded read
```

У совпадений есть роли:

1. `emit` — место фактически испускает код;
2. `declare` — место объявляет его в явной карте;
3. `reference` — место только упоминает код.

При одинаковом коде предпочтение получает `emit`, затем `declare`, затем
`reference`. Динамический хвост вроде `some_code:<value>` канонизируется к
известной базовой форме только тогда, когда такая база действительно есть в
карте диагностики.

Критическая граница: диагностический маршрут доказывает владельца проверки или
детектора. Он **не** доказывает runtime root cause. Для последнего нужны свежие
trace, путь исполнения, входные данные и наблюдаемый результат.

## 7. Переносимая архитектура

Система состоит из стабильного ядра и тонких адаптеров.

```text
                 ┌──────────────────────────┐
                 │     Универсальное ядро    │
                 │ schemas · navigation      │
                 │ strict gate · tracing     │
                 │ path safety · fail-close  │
                 └─────────────┬────────────┘
                               │
          ┌────────────────────┼────────────────────┐
          │                    │                    │
      project adapter      project adapter      project adapter
      manifest/stages      manifest/stages      manifest/stages
      diagnostics          diagnostics          diagnostics
      exclusions           exclusions           exclusions
```

### Ядро

Ядро:

- загружает только заранее разрешённый adapter;
- строит статический registry по активным источникам;
- выбирает stage/symbol/diagnostic/docs route;
- исполняет STOP-2;
- возвращает privacy-safe trace;
- останавливается при неизвестном проекте, цели или пути.

### Адаптер

Адаптер хранит только проектную декларацию:

- идентификатор и разрешённый root;
- retrieval manifest;
- stage map;
- diagnostic map;
- docs и focused tests;
- exclusions;
- local checks и владельцев маршрута.

Так новый проект не требует копировать ядро или добавлять специальные `if` по
всему коду. Он добавляет один проверяемый профиль.

## 8. Границы безопасности

Методика безопасна только при строгих границах чтения.

### Allowlisted roots

Вызывающий код передаёт `project_id`, а не произвольный путь. Реальный root
берётся из code-level allowlist. Неизвестный идентификатор — отказ.

### Относительные пути

Каждый маршрут внутри адаптера обязан быть относительным. Запрещены:

- абсолютные пути;
- `..` traversal;
- выход через symlink после `resolve()`;
- отсутствующие обязательные файлы.

### Exclusions

Даже в разрешённом root не всё является evidence. Политика исключений должна
закрывать чувствительные, временные, архивные, runtime- или write-ориентированные
зоны. Она применяется к sources, docs, tests, stages, diagnostics и готовым
records — не только к первому списку файлов.

### Статика вместо запуска

Для навигации используется статический AST-анализ. Runtime-модули не
импортируются и не выполняются: доказательный маршрут не должен случайно
инициализировать окружение, сеть или побочный эффект.

Принцип один: при сомнении не расширять доступ. Лучше вернуть «не могу
подтвердить из разрешённых источников», чем добыть правдоподобный ответ через
дыру в границе.

## 9. Граница между репозиториями

Внешний контекст закрыт по умолчанию. Он открывается только через явную
dependency card:

```text
scope_id
owner_project
consumer_project
contract_ref
reason
allowed_query_types: contract | interface
max_depth: 1
max_records: 2
transitive_traversal: false
```

Карточка разрешает прочитать только общий интерфейс или контракт. Она не даёт
право индексировать второй repository, читать его инциденты, историю или
внутреннюю реализацию. Если внешняя карточка указывает ещё на одну зависимость,
маршрут останавливается.

Практический образ: это дверной глазок, а не ключ от второго дома.

## 10. Как проверять методику

Хорошая проверка начинается до оценки результата.

### Сначала валидировать форму

Статический validator проверяет:

- разрешённый root и checked-in manifests;
- существование активных sources, tests и docs;
- AST symbols;
- diagnostic literals внутри заявленного owner symbol;
- exclusions;
- path containment;
- ограничения dependency card.

Если эта форма невалидна, красивые метрики не имеют веса.

### Разделить generator и scorer

Inputs фиксируются отдельно от labels. Generator видит только разрешённые
inputs, строит predictions и не читает labels. Отдельный scorer открывает labels
после того, как predictions зафиксированы.

Набор обязан содержать:

- положительные случаи с точным владельцем;
- отрицательные случаи, где правильный ответ — abstain;
- неоднозначные и near-miss случаи;
- проверки leakage, budgets и privacy.

Считаются не только попадания, но и:

```text
false selection  — выбрана неверная цель
false abstention — пропущена доступная верная цель
false completion — частичный span выдан за завершённое доказательство
```

Первый tool/contract/parsing failure останавливает batch до выяснения причины.
Иначе набор ошибок может выглядеть как качество модели, хотя сломан был первый
слой данных или маршрута.

## 11. Результаты и ограничения

Локальная проверка поддерживает ограниченные утверждения:

- точный target можно надёжно читать через strict gate;
- статический diagnostic route может привести к владельцу проверки;
- budgets и fail-close можно проверить автоматически;
- adapter можно переносить между разными кодовыми базами через manifests.

Она **не** поддерживает следующие утверждения:

- свободный естественный язык решён как autonomous router;
- candidate card является evidence;
- diagnostic owner равен runtime root cause;
- локальный тест доказывает production;
- текущие лимиты универсальны;
- один успешный adapter означает готовность всего монорепозитория.

Методика ценна именно тем, что не перепрыгивает через эти границы.

## 12. Память и адаптивность

Внешняя работа по experience-aware harnesses дала полезные идеи: per-case
outcomes, distilled patterns, bounded retrieval и correctness-first выбор. Это
вдохновение для гипотезы, а не перенос готового результата.

Память разделяется на два слоя:

- **Layer A: outcomes.** Privacy-safe append-only записи со ссылками,
  агрегированными флагами, hints и anti-examples; без сырых логов, запросов,
  source bodies и секретов.
- **Layer B: patterns.** Обобщения нескольких независимых случаев. Для
  продвижения нужны минимум три независимые поддержки, антипримеры, свежий
  holdout и отдельный scorer.

В локальных экспериментах bounded experience улучшил target recall с `18/22`
до `19/22`, но полный строгий путь остался `6/22`. Поэтому H1 — valid fail;
H2 — только structural pass; H3 — not evaluable; H4 — blocked. Одобренных
паттернов нет.

Следствие: память может быть журналом и источником будущих экспериментов, но не
имеет права менять selector, gate, prompt, runtime, модель или provider. Для
возобновления нужны техническая изоляция входов и независимый scorer.

## 13. Как поддерживать живой документ

У методики должно быть одно каноническое место. Остальные документы могут
ссылаться на него, но не должны создавать вторую правду.

Правила обновления:

1. Версионировать структурированные схемы и контракты.
2. Добавлять эксперименты append-only: дата, scope, integrity, агрегированные
   метрики, verdict, exclusions и следующий шаг.
3. Не переписывать старый verdict молча; добавлять датированную коррекцию.
4. Держать стабильные заголовки и anchors.
5. Не переносить в статью сырые запросы, логи, payloads, source bodies, labels
   или секреты.
6. Явно отмечать, что documentation evidence не меняет runtime или production.

### Чеклист изменения

- Это единственное каноническое место для правила?
- Новая запись имеет версию, дату и стабильный anchor?
- Она отделяет экспериментальный факт от общего принципа?
- Указано, что доказано, что исключено и что делать дальше?
- Нет ли в ней чувствительных данных или конкретных operational деталей?

## 14. Рецепт внедрения в новом репозитории

1. **Назначить идентичность.** Выбрать `project_id`, канонический контур,
   owner и rollback owner. Если этого нет — fail closed.
2. **Создать adapter.** Явно разрешить root и связать его с manifest, stage map,
   diagnostic map и canonical history route.
3. **Описать evidence map.** Включить только актуальные sources, docs и focused
   tests; создать exclusions.
4. **Добавить static validator.** Проверить схемы, paths, AST symbols,
   diagnostics, exclusions и dependency cards.
5. **Подключить navigation.** Возвращать candidate-only `target_spec` для
   stage/symbol/diagnostic/docs.
6. **Подключить strict gate.** Требовать exact target и enforce STOP-2.
7. **Собрать blind acceptance.** Разделить inputs/labels, подготовить positive и
   negative cases, независимый scorer и budget metrics.
8. **Пройти аудит.** Отдельно проверить root safety, exclusions, leakage,
   cross-project границы и отсутствие runtime effects.
9. **Продвигать постепенно.** `validating → pilot_ready → shadow/warn` только
   после новых доказательств. Production — отдельная задача.

10. **Подключить documentation gate.** После VERIFY формировать строгую
    privacy-safe квитанцию, направлять факт ровно в один канонический документ и
    отделять техническую проверку от человеческого разрешения на правку.
11. **Защитить внешние записи от повторов.** Для каждой разрешённой операции
    фиксировать точный набор входов, fingerprint авторизации и проверенный
    outcome. Повторный запуск завершать безопасным no-op, а не второй записью.

### Анти-паттерны

- назначать владельца по памяти;
- искать по всему filesystem вместо `project_id`;
- выдавать FTS-card за доказательство;
- превращать history в current-source truth;
- разрешать arbitrary root или абсолютные пути;
- читать второй repository без dependency card;
- расширять budget без нового основания;
- включать adaptive behavior по нескольким удачным примерам;
- объявлять local test production proof.

## 15. Документация как проверяемый маршрут

Живой документ нельзя надёжно поддерживать только обещанием «обновить потом».
После завершённого VERIFY нужен отдельный маршрут, который сохраняет кандидатный
факт в момент появления, но не публикует его автоматически:

```text
VERIFY receipt
  → schema validation
  → append-only candidate queue
  → canonical owner resolution
  → human approval
  → explicit patch plan
  → separate docs edit and static check
```

Квитанция содержит только необходимое: идентификаторы проекта и темы, тип
изменения, краткий факт, ссылки на evidence, результат проверки, время и при
необходимости заменяемый anchor. Она не должна содержать секреты, сырые логи,
payloads, transcripts, customer data или произвольные абсолютные пути.

Технически проверенный факт может ждать в очереди без человеческого одобрения.
Это позволяет не потерять знание, но ещё не разрешает менять документацию.
План правки появляется только когда одновременно выполнены условия:

- проверка завершилась успешно и имеет timestamp;
- есть конкретные evidence references;
- человек одобрил публикацию;
- канонический документ выбран checked-in картой владельцев;
- никакие флаги runtime, production или внешней записи не включены.

Сам gate не редактирует документы, не пишет в систему памяти, не запускает
runtime и не делает production-утверждений. Его задача уже: доказуемо доставить
один факт к одному владельцу и остановиться перед побочным эффектом.

Коррекция старого знания оформляется новой записью со ссылкой на заменяемый
anchor. Старый вывод не стирается молча: остаются видны исходная формулировка,
новое evidence и причина изменения.

## 16. Идемпотентность внешних записей

Даже точная авторизация опасна, если один и тот же batch можно случайно запустить
дважды. Поэтому внешняя запись должна иметь отдельный outcome ledger — безопасный
журнал уже выполненных операций без исходных чувствительных текстов.

Минимальный контракт такого журнала:

```text
authorization fingerprint
exact source identities
exact content fingerprints
returned target identities
verification result for every record
explicit no-mutation / no-delete boundaries
```

Перед новой записью исполнитель обязан проверить одновременно авторизацию и
ledger. Если точный набор уже выполнен и проверен, правильный ответ —
`already_applied` с нулём writable operations. Если ledger отсутствует,
повреждён или не совпадает с авторизацией, путь закрывается до ручного разбора;
он не должен считать batch новым только потому, что доказательство прошлого
запуска не прочиталось.

После каждой отдельной записи безопасные metadata считываются обратно и
сверяются с разрешённым fingerprint. Первый mismatch или tool failure
останавливает весь batch. Такой порядок защищает от дубликатов, частичного
успеха, подмены содержания и повторного использования устаревшего разрешения.

## 17. Текущая зрелость и оставшиеся работы

Методика уже подтверждена как локальный developer workflow в нескольких
независимых адаптерах. Работают строгая маршрутизация по точной цели, STOP-2,
fail-close проверки путей, ограниченные межпроектные dependency cards,
append-only documentation queue и защита разрешённых внешних batch-записей от
повтора. Узкие статические и контрактные проверки проходят совместно.

Это всё ещё не означает готовность каждого репозитория и не делает систему
автономным инженером. Текущий честный статус:

| Область | Что уже есть | Что остаётся |
|---|---|---|
| Навигационное ядро | strict target, bounded read, privacy-safe trace | расширять только по новым benchmark evidence |
| Проектные адаптеры | несколько локальных pilot-ready профилей | подключить оставшиеся репозитории и их owners |
| Общий инфраструктурный код | узкие interface-only dependency cards | не открывать весь общий repository без доказанной нужды |
| Документация | VERIFY capture, owner routing, human patch plan | накопить реальные approved updates и проверить удобство процесса |
| Историческая память | provenance и idempotent bounded writes | разбирать оставшийся backlog только новыми отдельными разрешениями |
| Адаптивность | outcome schema и экспериментальные границы | собрать независимые outcomes, holdout и scorer; behavior оставить выключенным |
| Production | граница явно отделена | каждый production-вывод подтверждать свежим live proof отдельно |

Ближайшие практические работы:

1. Назначить отсутствующих human owner и rollback owner, не заполняя их по
   памяти.
2. Добавлять адаптеры по одному: identity, root, manifests, docs, stages,
   diagnostics, exclusions, local checks и отрицательные тесты.
3. Для неоднозначных соседних репозиториев сначала зафиксировать ownership
   boundary и только затем разрешать маршрутизацию.
4. Провести реальные пилоты documentation gate: от VERIFY receipt до
   одобренной правки и повторной статической проверки.
5. Сохранять adaptive behavior выключенным, пока независимый benchmark не
   покажет улучшение полного строгого пути, а не только candidate recall.
6. Не расширять shared scopes и context budgets заранее: каждое расширение
   требует нового evidence и отдельной проверки безопасности.

Критерий зрелости здесь не число подключённых репозиториев. Метод становится
сильнее, когда новый адаптер сохраняет те же свойства: точная цель, небольшой
контекст, проверяемый источник, честное воздержание и отсутствие скрытых
побочных эффектов.

## Приложение: минимальный словарь

| Термин | Значение |
|---|---|
| Candidate | Навигационная подсказка; не доказательство. |
| Evidence | Прочитанный выбранный source span, symbol, contract anchor или test. |
| Owner | Точный источник, отвечающий за этап, правило или diagnostic signal. |
| Adapter | Проектная декларация поверх универсального ядра. |
| Manifest | Список разрешённых evidence sources и exclusions. |
| STOP-2 | Строгий начальный конверт чтения. |
| Fail closed | При неясности отказаться, а не расширять поиск. |
| Dependency card | Явное одношаговое разрешение на интерфейсный контекст другого репозитория. |
| Blind acceptance | Проверка, где generator не видит labels, а scorer отделён. |

## Дальнейшее развитие

Следующие улучшения должны добавляться только как новые проверяемые гипотезы:
с заранее закреплёнными входами, holdout-набором, независимым scorer и явным
решением о том, что меняется или остаётся выключенным. Методика должна расти не
от числа страниц, а от качества новых доказательств.
