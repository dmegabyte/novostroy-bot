# NMBot Product Contract

**Статус:** proposed. Этот документ задаёт границу V6 product work; он не
меняет runtime, prompts, deployment или production.

## 1. Зачем нужен бот

Ирина помогает клиенту с выбором новостройки в Москве и МО. Цель не в том,
чтобы как можно скорее передать диалог оператору: сначала дать полезный,
честный ответ, затем уточнить выбор и только после этого предложить следующий
шаг с человеком.

Короткая формула: **польза → уточнение → специалист при необходимости**.

## 2. Что клиент должен получать

- Короткий и понятный ответ, а не каталог или техническое объяснение.
- До трёх подходящих вариантов при поиске, с реальными подтверждёнными данными.
- Один ясный следующий шаг за сообщение.
- Честное сообщение о том, чего в данных нет.
- Предложение специалиста только когда данных недостаточно или клиент готов
  продолжить с человеком.

Бот не называет неподтверждённые цену, готовность, инфраструктуру, ипотечные
условия, скидки или наличие. Он не обещает наличие и не просит телефон до
согласия на контакт.

## 3. Что не входит в продукт

- Ирина не является универсальной энциклопедией по недвижимости или
  ипотечным калькулятором.
- Product Contract не задаёт JSON-схемы, prompt-тексты, systemd, shell-команды,
  секреты, deploy или incident repair.
- Новый частный пример не создаёт новый сценарий, runtime, router или правило.
  Сначала он должен относиться к одному из пяти сценариев ниже; новый сценарий
  требует отдельного продуктового решения и измеримого acceptance.
- Бот не заменяет специалиста там, где источник данных не подтверждает условия,
  но и не передаёт клиента специалисту вместо доступной полезной помощи.

## 4. Пять основных сценариев V6

| Сценарий | Польза для клиента | Следующий шаг |
|---|---|---|
| Новый подбор | Варианты по району, бюджету, комнатам и другим условиям | Выбрать ЖК или уточнить условие |
| Уточнение подбора | Обновлённые или отфильтрованные варианты без потери контекста | Уточнить одно следующее условие |
| Выбранный ЖК | Ответ по уже показанной карточке | Сравнить, проверить или продолжить подбор |
| Ипотека и первоначальный взнос | Только подтверждённые условия либо честная граница знания | Предложить специалиста, затем спросить телефон только после «да» |
| Прямой запрос специалиста | Быстрый и понятный переход к человеку | Согласие, затем номер телефона |

## 5. Как это работает — короткая карта

```text
Jivo сообщение
  → bridge передаёт его в выбранный API runtime
  → runtime определяет сценарий и хранит контекст диалога
  → при реальном подборе или проверке объекта получает факты через search/MCP
  → нормализованная карточка facts / near / missing
  → composer пишет клиентский ответ только по этой карточке
  → при недостатке данных: предложение специалиста
  → согласие клиента → runtime запрашивает телефон
  → bridge отправляет готовый ответ в Jivo
```

### Кто за что отвечает

| Компонент | Владелец решения | Что он не делает |
|---|---|---|
| Router / runtime | Сценарий, состояние, согласие и переход к телефону | Не придумывает свойства ЖК |
| Search / MCP | Поиск и проверяемые данные об объектах | Не пишет клиентский текст и не принимает телефон |
| Карточка фактов | Разделяет `facts`, `near` и `missing` | Не превращает пожелание клиента в факт |
| Composer | Коротко объясняет данные и один следующий шаг | Не добавляет факты из памяти или общих знаний |
| Bridge / Jivo | Доставляет результат между Jivo и API | Не меняет продуктовый сценарий |

**Когда запускается поиск.** Поиск нужен для нового подбора, существенного
изменения условий или проверки выбранного объекта. Короткое уточнение может
использовать уже показанные карточки. Финансовый вопрос без выбранного объекта
не превращается в выдуманный поиск: бот либо опирается на подтверждённые данные,
либо честно объясняет границу и предлагает специалиста.

## 6. Измеримая граница качества

Изменение входит в V6 product release, только если оно улучшает один сценарий
из таблицы выше или защищает подтверждённость фактов/согласие на контакт.

Product candidate принимается только когда на одном `source_sha` и одном наборе
immutable artifact hashes:

1. проходят **5 из 5** сценариев из раздела 4;
2. в проверенных ответах **0 неподтверждённых фактов**;
3. новый подбор показывает не больше трёх вариантов и задаёт ровно один
   следующий вопрос;
4. телефон запрашивается **0 раз до явного согласия** клиента;
5. для каждого live-сценария есть связанный privacy-safe trace
   `bridge → intended API → terminal Jivo outcome`.

Это release acceptance, а не SLA production. Численный latency/error budget
добавляется только после измеренного baseline и отдельного продуктового решения;
его нельзя выдумывать ради полноты документа.

Локальные тесты и health необходимы, но не доказывают качество для клиента.
Для Jivo-релиза нужны: точный immutable artifact, проверка выбранного контура,
связанный trace `bridge → intended API → terminal Jivo outcome` и успешный
сценарий. Ошибка останавливает batch; исправление выходит новым commit и новым
release ID.

## 7. Где лежат детали

- Фактическая V6-механика: `../nmbot_v6/simple_contract.py`,
  `../nmbot_v6/simple_runtime.py` и два файла в `../prompts/`.
- Проверяемые примеры: `../tests/test_nmbot_v6_simple_contract.py`,
  `../tests/test_nmbot_v6_simple_runtime.py` и
  `../tests/test_nmbot_v6_finance_prompt.py`.
- Контракты Jivo, bridge и CRM: `NMBOT_EXTERNAL_CONTRACTS.md`.
- Краткая карта runtime: `CURRENT_ARCHITECTURE.md`.
- Сборка, rollout и rollback: `NMBOT_RUNBOOK.md` и
  `NMBOT_VERSION_BUILD_PLAN.md`.
- Принятые и заменённые решения: `DECISIONS.md`.

Этот файл намеренно не содержит JSON-схем, systemd, shell-команд, секретов и
внутренних prompt-текстов: это технические детали, а не продуктовый контракт.
