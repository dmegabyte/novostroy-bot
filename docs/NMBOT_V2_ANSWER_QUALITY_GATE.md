# NMBOT V2 Answer Quality Gate

Единый контрольный стандарт для V2 `search + answer`. Целевой уровень — **UX 9–10/10**: Ирина звучит как цифровой менеджер по продажам новостроек, а не как каталог или техотчёт.

Шкала зрелости всего проекта и точные критерии 10/8/6/4/2/0 по восьми
параметрам находятся в `docs/NMBOT_V2_PROJECT_QUALITY_SCORECARD.md`.

## 1. Layered gate

Проверка всегда идёт по слоям:

1. **Search / MCP** — V2 search-agent возвращает строгий JSON `facts[]`, `near[]`, `missing`, `params`, `diagnostics`; `facts` и `near` не смешиваются.
2. **Normalized Card** — runtime превращает MCP/search JSON в нормальные `OptionCard`: максимум три карточки, только подтверждённые поля.
3. **Response** — runtime собирает клиентский текст из проверенного `ResponsePlan`.
   Deterministic renderer является безопасным fallback. Composer может быть включён
   для V2/V3 режимом `off|shadow|publish`: `shadow` не публикует модельный текст,
   `publish` публикует только механически валидный результат, а `off`/ошибка оставляют
   deterministic fallback.
4. **Dialogue / State** — уточнения, выбранный ЖК, financing overlay и operator flow не теряют контекст.
5. **Cost / Latency** — для offline harness внешние расходы отсутствуют; live/model-cost проверяется отдельно, если такой прогон разрешён.

Для search-контракта используется единый исход: `valid`, `degraded` или `invalid`.
В production V0/V2/V3 это report-only диагностика: `degraded` и `invalid` не
скрывают sanitized identifiable cards, а пишутся как bounded
`search_validation_report`. Malformed/unidentifiable data и exact named scope
остаются блокирующими. В этом offline quality gate статус `invalid` по-прежнему
означает, что сценарий не прошёл оценку, даже если production показал карточку.

## 2. Hard blockers

Любой blocker = сценарий не прошёл, даже если сумма баллов высокая:

- invented fact: название, цена, метро, школа, парк, срок, отделка, ипотека или спрос не подтверждены `facts[]` / `near[]`;
- MCP / JSON / internal leak: `mcp`, `json`, `regex`, `diagnostics`, traceback, payload и похожая техническая кухня в клиентском ответе;
- technical honesty phrasing: клиентский ответ говорит о «безопасном контексте»,
  «карточках и личных данных», внутренней валидации или другой кухне вместо
  простого человеческого объяснения, чего сейчас нельзя подтвердить;
- violated hard constraints: `facts[]` нарушает `effective_hard` или не имеет evidence по hard-полю; это offline quality blocker и production report-only event, а не причина скрыть карточку;
- facts / near mixing: альтернатива выдана как точное совпадение;
- больше трёх карточек;
- ноль или больше одного финального вопроса;
- false inventory absence: ответ говорит «нет вариантов», хотя `facts[]` есть;
- stale context: уточнение или выбранная карточка обрабатываются как новый пустой диалог;
- early operator: оператор предлагается вместо полезного ответа при наличии карточек;
- duplicate answers: одинаковые блоки или повтор одного и того же ответа.
- duplicate intro / summary: нельзя подряд писать «нашла варианты» и отдельной строкой повторять тот же счётчик, например «Нашла 3 подходящих варианта»;
- internal enum / anglicism: клиент не должен видеть внутренние enum-значения и англицизмы вроде `white box`; для клиента это **предчистовая отделка**;
- repeated identical benefit: разные карточки не могут получать одну и ту же benefit-фразу, даже если у них похожие поля;
- conflating data semantics: `counter_novos.count_ads` / `ads_count` — это объявления на витрине, не продажи; продажами можно называть только подтверждённый `sales_count` / ЕГРН;
- one-line dry card: карточка с сильными facts не проходит, если это одна длинная строка без отдельной причины презентации.

## 3. Scored dimensions

Каждый сценарий получает пять оценок по 0–2, всего 10:

| Dimension | 2 | 1 | 0 |
|---|---|---|---|
| Facts | все конкретные факты grounded | мелкая шероховатость без выдумки | invented / unsupported / technical leak |
| Completeness | использованы доступные сценарные факты | часть доступных сильных фактов потеряна | нет полезного следующего шага или ложная пустота |
| Beauty | живой короткий ответ, читабельная структура | суховато или плотновато | техотчёт, простыня, плохая структура |
| Scenario fit | сценарий распознан и раскрыт | сценарный акцент слабый | сценарий перепутан |
| Dialogue continuity | один финальный вопрос, контекст сохранён | вопрос/контекст частично слабые | 0/>1 вопросов, stale context, early operator |

**Pass только если score >= 9 и hard blockers отсутствуют.**

Даже при сумме 9+ оценки **Beauty=2** и **Scenario fit=2** ставятся только если карточки читаются как презентация: когда facts поддерживают сценарий, у каждого объекта есть связка **факт → отличие → польза**. Сухое перечисление полей, повтор одной benefit-фразы и сценарный факт без объяснения пользы дают максимум 1 по соответствующей размерности или hard blocker, если карточка фактически не презентована.

## 4. Scenario expectations

- **Family** — семейная польза из фактов: школы, сады, парк, двор без машин, детские/спортивные площадки, безопасность, транспорт. Нельзя писать семейную инфраструктуру, если её нет.
- **Investment** — цена и порог входа, скидки/ипотека/ЕГРН/счётчики только если они есть; 2–3 варианта с разными инвестиционными акцентами; без обещания доходности или роста цены.
- **Rental** — арендо-пригодный вход: компактность, отделка, метро, готовность, район, подтверждённый спрос только по MCP-сигналам; без ставки аренды и окупаемости.
- **Life** — удобство жизни: локация, транспорт, отделка/готовность, парки/вода, территория, безопасность, паркинг, лифты — только из карточки.
- **Financing overlay** — ипотека/рассрочка/взнос/ставка как слой поверх primary scenario. Если ставка или взнос не пришли, не придумывать цифры и не обещать одобрение.

Семантика счётчиков:

- `sales_count` / ЕГРН — можно описывать как продажи или сделки, если поле реально есть;
- `ads_count` / `counter_novos.count_ads` — только «объявления», «витрина», «текущий выбор»; нельзя называть спросом, продажами, ликвидностью или сделками.
- **Refinement** — уточнение не начинает диалог заново; прошлый контекст сохраняется, новые hard/preference условия видны.
- **Near / no-results** — если `near[]` есть, показать 1–2 ближайших варианта и отличие. Если нет ничего, предложить ослабить один параметр или проверку человеком.
- **Selected-card** — отвечать из выбранной `OptionCard` / сохранённого search snapshot, без нового широкого поиска и без выдуманных detail-полей.
- **Operator flow** — оператор только когда данных объективно не хватает, клиент выбрал ЖК и хочет актуальность, либо сам просит человека. Не обещать звонок до номера.

## 4.1 Offline quality-harness: контракт компоновщика ответа

Production V2 не отдаёт composer право менять stage, recipe, порядок карточек,
anchor или CTA. Боевой runtime собирает текст из проверенного `ResponsePlan`:
deterministic renderer используется как fallback, а feature-gated composer в
режиме `publish` может заменить только безопасную форму ответа. Описанный ниже
contract используется и production-путём, и offline quality-harness, regression
tests и ручным сравнением качества — в зависимости от режима.

LLM отвечает за естественную формулировку, но не за разметку и не за сборку
всего сообщения в одном плоском поле. Его строгий JSON имеет вид:

```json
{
  "intro": "Короткий ответ на текущий запрос",
  "options": [
    {
      "name": "Точное имя из canonical_cards",
      "facts": "Только подтверждённые характеристики",
      "description": "Почему эти факты важны в текущем сценарии"
    }
  ],
  "missing_note": "Необязательная честная оговорка",
  "final_question": "Ровно один следующий вопрос?"
}
```

- `intro` отвечает на текущий ход и acknowledgement, не пересказывает список;
- каждый ЖК — отдельный объект, `facts` и `description` не смешиваются;
- `missing_note` пустой, если честной оговорки нет;
- вопросительный знак разрешён только в `final_question`;
- runtime проверяет каждый блок по `ResponseBrief`, затем собирает итоговый текст.
  Плоское модельное поле `response` не публикуется и не разбирается.

Если primary/repair/retry компоновщика не дал валидную структуру,
quality-harness сравнивает сценарий с deterministic renderer и помечает blocker
`composer_degraded_fallback`. Это не означает production outage: runtime возвращает
deterministic fallback и сохраняет runtime-owned stage/recipe/order/CTA.

Fallback обязан соблюдать тот же человеческий тон, что и компоновщик: без
технических терминов, с честной границей и одним понятным следующим шагом.

## 5. Exact report row format

```text
Scenario | Search/MCP | Card | Response | Facts | Completeness | Beauty | Scenario fit | Dialogue | Score | Verdict | Layer to fix
```

## 6. First-Failure procedure

1. Запускаем сценарии последовательно.
2. При первом fail batch останавливается.
3. Смотрим слой:
   - Search/MCP fail → чинить search prompt / contract / MCP request profile.
   - Search good, Card bad → чинить normalization / `OptionCard` mapping.
   - Card good, Response bad → чинить response renderer / presentation.
   - Response good, но сценарий или контекст потеряны → чинить state / planner.
4. После фикса сначала rerun только упавший case.
5. Потом полный offline-15.

## 7. Automation vs manual read

Автоматические assertions обязательны: они ловят контракт, блокеры, вопрос, количество карточек и грубые unsupported claims. Но финальную клиентскую копию всё равно нужно читать глазами: Ирина должна звучать как живой консультант. Для этого стандарта **не нужны внешние judge/model calls**.

Каждый запуск имеет уникальный `run_id`, хэши fixture-файлов и
`prompt_set_id`. Offline replay помечает prompt set как `configured_only`, а
разрешённый live run — только реально вызванные search/one-shot composer prompt
как `complete`. Подробный контракт: `docs/NMBOT_PROMPT_PROVENANCE.md`.

## 8. V1 как библиотека удачных диалогов

V1 разрешено и нужно использовать как источник проверенных приёмов общения:

- живых вступлений и переходов между шагами;
- удачных презентаций family / investment / rental / life;
- ответов по выбранному ЖК;
- естественных уточнений, сравнений и operator handoff;
- формулировок, которые уже проходили ручной dialogue review.

При этом V1 **не является источником архитектуры V2**. Нельзя переносить целиком V1 routing, state branches, fuzzy-эвристики, fallback-цепочки или готовый текст без повторной проверки фактов.

Правило переноса:

1. Найти удачный V1-диалог в `logs/dialog_reviews.md`, `logs/stateful_dialog_reviews.md` или production dialogue journal.
2. Отделить универсальный приём общения от конкретных данных и legacy routing.
3. Проверить каждое утверждение по V2 `facts[] / near[] / missing`.
4. Перенести приём как style/example regression, а не как жёсткую фразу на конкретный запрос.
5. Прогнать V2 quality gate и вручную сравнить читаемость с V1 baseline.

Если V1-вариант звучит лучше, а V2 фактически корректен, это считается gap слоя presentation/response. Если V1 сам содержит выдумку, технический термин, stale context или старую routing-ошибку, такой пример не переносится.
