# Карта сценариев и механик полей NMBOT

Статус: проектный источник правил и документация исполняемого динамического
`WritingPlan`.

Этот документ детализирует релизный `docs/SCENARIO_MCP_CONTRACT.md` до уровня
`scenario × canonical fact → communication mechanics`. Для структуры
смысловых коридоров также использована историческая карта
`docs/reason_scenario_templates_v3.json`, но её taxonomy и готовые фразы не
считаются текущим runtime-контрактом.

Текущие исполняемые источники:

- поиск и wire-поля — `nmbot_v2/search_contract.py`;
- нормализация — `nmbot_v2/card_normalizer.py`;
- клиентская карточка — `nmbot_v2/contracts.py::OptionCard`;
- выбор сценария — `nmbot_v2/scenario_recipes.py`;
- mechanics, scope и выбор акцента — `nmbot_v2/scenario_field_mechanics.py`;
- model-facing payload — `nmbot_v2/contracts.py::ResponseBrief`.

Карта подключена к composer через `ResponseBrief.scenario_context`. V0 всегда
использует deterministic renderer. V2 и V3 могут независимо подключать composer
через `NMBOT_V2_RESPONSE_COMPOSER_MODE=off|shadow|publish` и
`NMBOT_V3_RESPONSE_COMPOSER_MODE=off|shadow|publish`; до включения своего флага
каждая версия остаётся deterministic. `shadow` не меняет клиентский текст, а
`publish` использует модельный результат только после механической проверки и с
deterministic fallback. Общий writer prompt не содержит все сценарии
одновременно: код передаёт только активный блок.

## 1. Четыре независимые оси

### 1.1. Основной сценарий покупателя

В один момент активен один основной сценарий:

| ID | Задача клиента |
|---|---|
| `life` | Выбор квартиры для собственной жизни без более узкого мотива. |
| `family` | Выбор для семейной жизни и семейного распорядка. |
| `investment` | Сравнение объекта как покупки капитального актива без обещаний результата. |
| `rental` | Выбор объекта, который планируется готовить под сдачу, без обещаний дохода или спроса. |

Исторический `self_use` переименован по смыслу в `life`.

### 1.2. Наложение

`financing` — не замена основного сценария, а наложение (`overlay`). Например,
`family + financing` сохраняет семейные акценты и добавляет только подтверждённые
условия оплаты.

### 1.3. Фасеты запроса

Фасет меняет порядок полей, но не заменяет смысл основного сценария:

| Facet | Что меняет |
|---|---|
| `budget` | Поднимает цену и ценовой диапазон в начало сравнения. |
| `metro_access` | Поднимает подтверждённое метро и транспортный маршрут. |
| `fast_move` | Поднимает готовность и отделку, но не разрешает обещать ключи или немедленный переезд. |
| `location` | Поднимает географию и маршрут. |
| `rooms` | Поднимает комнатность и доступные форматы. |
| `readiness` | Поднимает статус/срок готовности. |
| `finishing` | Поднимает подтверждённый тип отделки. |

Ипотека, рассрочка и скидка входят в наложение `financing`, а не в этот список.

### 1.4. Этап диалога

`first_list`, `refinement`, `current_options`, `selected_object`, `no_results`,
`near_results`, уточнение финансирования и передача оператору — этапы ответа, а
не сценарии покупателя. Они определяют количество карточек, CTA и форму ответа,
но не должны менять смысл полей `family / life / investment / rental`.

## 2. Механика прохождения поля

```text
MCP wire fields
  → card_normalizer
  → canonical OptionCard fact
  → active scenario × fact rule
  → per-card ScenarioAngle
  → ResponseBrief / WritingPlan
  → Gemini 2.5 Flash: primary simple JSON
  → if invalid but recoverable: Ling 2.6 Flash JSON normalization
  → mechanical integrity check
  → assembled candidate / deterministic fallback
```

Gemini сам формирует простой JSON
`{intro, cards[{name,text}], recommendation, missing_note, final_question}`. При
валидном результате Ling не вызывается. Ling не выбирает факты и не редактирует
стиль: он получает исходный ответ Gemini только при восстанавливаемой ошибке
JSON и исправляет формат без изменения клиентской прозы. Runtime проверяет
полное сохранение текста после такого исправления, имена и порядок карточек,
CTA, числа и названия ЖК. Пустой, transport/provider или явно обрезанный ответ
Gemini получает один повтор тем же writer prompt; только после повторного сбоя
runtime использует deterministic fallback. V0 не подключён к этому pipeline,
потому что у него нет безопасного адаптера `ResponseBrief/WritingPlan`.

Для каждой карточки код передаёт модели не готовую рекламную фразу, а смысловой
коридор:

```json
{
  "card_name": "ЖК …",
  "anchor_fact": "readiness",
  "evidence": {"ready": "сдан"},
  "communication_goal": "объяснить, какой горизонт ожидания подтверждён для семьи",
  "allowed_concepts": ["готовность дома", "подтверждённый срок", "ожидание строительства"],
  "forbidden_meanings": ["ключи уже выдают", "можно сразу переехать", "заселение доступно сейчас"],
  "card_mode": "normal"
}
```

Это не шаблон фразы. Модель сама выбирает живую формулировку, но не выходит за
границы evidence и активного сценария.

себе не являются текущим wire-контрактом, если normalizer их явно не поддержал.

## 4. Общие правила полей

Эти ограничения действуют во всех сценариях:

| Поле | Всегда допустимо | Всегда запрещено без отдельного evidence |
|---|---|---|
| `apartment_price` | «Квартиры в проекте — от …», сравнение нижних границ | цена нужной комнатности, попадание в бюджет, скидка, выгода |
| `readiness` | фактический статус или подтверждённый горизонт ожидания | выдача ключей, доступность квартиры, немедленный переезд, отсутствие задержек |
| `finishing` | подтверждённый тип отделки и объём стартовых работ | «ремонт не нужен», точная экономия, готовность к заселению/аренде |
| `metro` | станция и подтверждённое время/способ пути | престиж района, спрос, ликвидность, гарантированно короткая дорога без времени |
| `location` | название географии | школы, парки, престиж, экология или транспорт, если их нет отдельными facts |
| `area` | подтверждённый диапазон площади | конкретная планировка, спальни, кухня или просторность без evidence |
| `sales_count` | буквальный счётчик и дата, если есть | спрос, ликвидность, рост цены, качество сделки |
| `ads_count` | буквальный текущий счётчик витрины | спрос, дефицит, скорость продажи/сдачи |
| `developer` | подтверждённое имя | надёжность, качество и сроки без отдельных фактов |
| `property_class` | подтверждённый класс | качество жизни, статус или доходность как автоматический вывод |
| `daily_services` | буквальные магазины/сервисы/аптеки из evidence | близость, «всё необходимое», пешая доступность без расстояния |
| `healthcare` | буквальный медицинский ориентир | качество медицины, места, здоровье или безопасность |
| `ecology_rating` | само значение рейтинга | «экологически чисто», польза для здоровья, безопасность |
| `transport_access` | ж/д, шоссе, расстояние от МКАД | престиж, спрос, экономия времени без времени пути |
| `parking` | факт наличия паркинга | наличие свободного места, бронь или дефицит |
| `room_specific_price` | буквальная комнатность и её цена | наличие такого лота, попадание в бюджет, выбранный лот |
| `price_per_m2` | буквальная цена за м² | выгода, доходность, рост цены или окупаемость |

## 5. Основной сценарий `life`

Цель: помочь сравнить практичность вариантов для собственной жизни.

| Приоритет | Fact | `communication_goal` | `allowed_concepts` | `forbidden_meanings` |
|---:|---|---|---|---|
| 1 | `metro` | Объяснить, какой ежедневный маршрут подтверждён. | станция, способ пути, время пути, повседневные поездки | престиж района, ликвидность, экономия времени без подтверждённого времени пути |
| 2 | `daily_services` / `healthcare` | Зафиксировать подтверждённые повседневные и медицинские ориентиры. | буквальные магазины, сервисы, аптеки, клиники | близость, качество, полнота инфраструктуры без evidence |
| 3 | `readiness` | Объяснить подтверждённый статус дома или срок ожидания. | готовность дома, стадия строительства, срок сдачи | выдача ключей, немедленное заселение, отсутствие задержек |
| 4 | `finishing` | Объяснить, какой тип отделки подтверждён и какую подготовку он предполагает. | наличие или отсутствие отделки, подтверждённый тип, соответствующий объём стартовых работ | переезд сразу, ремонт не нужен, точная экономия |
| 5 | `location` / `transport_access` | Зафиксировать географический и транспортный ориентир. | район, город, ж/д, шоссе, расстояние от МКАД | престиж, спрос, экономия времени без evidence |
| 6 | `parks` / `safe_yard` / `ecology_rating` | Объяснить только подтверждённые факты о прогулках, территории или рейтинге. | парк, вода, двор, площадка, буквальный рейтинг | экологичность, безопасность района, польза для здоровья |
| 6 | `area` / `room_formats` | Помочь сопоставить подтверждённый формат с бытовой задачей. | диапазон площади, доступные комнатности, набор форматов | конкретная планировка, отдельные комнаты или просторность без evidence |
| 7 | `apartment_price` | Зафиксировать нижнюю ценовую точку для сравнения вариантов. | нижняя граница проекта, стартовая цена как ориентир | попадание в бюджет, цена нужной квартиры, скидка или выгода |
| 8 | `developer` / `property_class` | Зафиксировать нейтральный подтверждённый профиль проекта. | имя застройщика, подтверждённый класс проекта | надёжность застройщика, премиальный образ жизни, лучшее качество |

## 6. Основной сценарий `family`

Цель: связать подтверждённые факты с семейным распорядком, не придумывая
качество инфраструктуры или доступность мест.

| Приоритет | Fact | `communication_goal` | `allowed_concepts` | `forbidden_meanings` |
|---:|---|---|---|---|
| 1 | `schools` | Объяснить, какая семейная инфраструктура подтверждена и чем она полезна при оценке ежедневной логистики. | школа, детский сад, подтверждённые семейные ориентиры | качество школы, гарантированное место, близость или точное время пути без evidence |
| 2 | `safe_yard` | Буквально назвать подтверждённый элемент двора без оценки его безопасности. | двор без машин, детская площадка, спортивная площадка, охрана — только буквально | безопаснее, безопасный двор, полная безопасность, дети могут гулять без присмотра, закрытая территория без evidence |
| 3 | `parks` | Объяснить подтверждённую возможность для прогулок. | парк, лес, набережная, вода рядом, прогулочный ориентир | гарантированная экология, безопасность, точная близость без evidence |
| 4 | `daily_services` / `healthcare` | Связать подтверждённые бытовые и медицинские ориентиры с оценкой семейной логистики. | магазины, сервисы, аптеки, клиники — только буквально | близость, качество, «всё необходимое», гарантии здоровья |
| 5 | `metro` | Объяснить подтверждённый маршрут для семейных ежедневных поездок. | поездки по делам, на работу и обратно, станция и способ пути | школа рядом только из-за метро, престиж района, короткая дорога без времени |
| 6 | `readiness` | Объяснить подтверждённый семейный горизонт ожидания. | статус дома, стадия строительства, заявленный срок сдачи | ключи, можно сразу переехать, точная дата заселения |
| 7 | `finishing` | Объяснить, какой тип отделки подтверждён и какой объём бытовой подготовки он предполагает. | наличие или отсутствие отделки, подтверждённый тип, соответствующий объём стартовых работ | переезд быстрее, ремонт не нужен, квартира готова к жизни |
| 7 | `area` / `room_formats` | Помочь оценить подтверждённый семейный формат. | диапазон площади, доступные комнатности, набор форматов | конкретные спальни, детская, кухня или удобная планировка без lot evidence |
| 8 | `apartment_price` | Зафиксировать ценовую точку для семейного сравнения. | нижняя граница проекта, стартовая цена как ориентир | точно укладывается в семейный бюджет, цена нужной квартиры, будущие платежи |
| 9 | `location` | Зафиксировать географию семейного поиска. | район, город, направление | семейная инфраструктура по одному названию района |

## 7. Основной сценарий `investment`

Цель: дать проверяемые точки сравнения покупки без прогноза финансового
результата.

| Приоритет | Fact | `communication_goal` | `allowed_concepts` | `forbidden_meanings` |
|---:|---|---|---|---|
| 1 | `apartment_price` | Зафиксировать подтверждённый порог входа для сравнения с другими проектами. | нижняя граница проекта, место в текущем ценовом сравнении | доходность, окупаемость, выгодная инвестиция, будущая цена, попадание в бюджет |
| 2 | `price_per_m2` | Зафиксировать подтверждённую цену за квадратный метр для нейтрального сравнения. | цена за м² | выгода, доходность, рост цены, окупаемость |
| 3 | `sales_count` | Зафиксировать подтверждённый счётчик сделок без рыночных выводов. | число сделок/записей ЕГРН, дата счётчика | спрос, ликвидность, надёжность, прогноз продаж |
| 3 | `ads_count` | Зафиксировать текущий счётчик витрины без вывода о спросе. | число объявлений на момент данных | дефицит, спрос, скорость продажи, ликвидность |
| 4 | `readiness` | Объяснить стадию проекта и строительный горизонт. | сдан, строится, срок, отсутствие ожидания стройки у готового дома | безрисковость, рост цены, быстрая перепродажа, отсутствие задержек |
| 5 | `room_formats` / `lot_examples` | Объяснить, какие форматы подтверждённо представлены. | подтверждённые комнатности, площади, lot examples | самый востребованный формат, легко сдать или продать, будущая доступность |
| 6 | `finishing` | Объяснить, какой тип отделки подтверждён и какую подготовку он предполагает. | наличие или отсутствие отделки, подтверждённый тип, соответствующий объём стартовых работ | готово к аренде, точные вложения, срок запуска |
| 7 | `metro` / `location` | Зафиксировать подтверждённый транспортно-географический профиль. | станция, способ пути, время пути, район или направление | арендный спрос, ликвидность, рост цены, престиж района |
| 8 | `developer` / `property_class` | Зафиксировать подтверждённый профиль проекта. | имя застройщика, класс проекта | гарантия качества, инвестиционный статус, надёжность застройщика |

Глобально запрещены: доходность, окупаемость, рост цены, спрос, ликвидность,
гарантия перепродажи и любые прогнозы результата сделки.

## 8. Основной сценарий `rental`

Цель: помочь выбрать объект для дальнейшей подготовки под сдачу, не утверждая,
что арендатор, спрос или доход уже существуют.

| Приоритет | Fact | `communication_goal` | `allowed_concepts` | `forbidden_meanings` |
|---:|---|---|---|---|
| 1 | `room_formats` / `area` | Объяснить, какие форматы объекта подтверждены для дальнейшей подготовки под сдачу. | подтверждённые комнатности, площадь, набор форматов | формат востребован, его легко сдать, конкретный профиль арендатора |
| 2 | `finishing` | Объяснить, какой тип отделки подтверждён и какую подготовку объекта он предполагает. | наличие или отсутствие отделки, подтверждённый тип, соответствующий объём стартовых работ | готово к аренде, можно сразу заселить арендатора, ремонт не нужен |
| 3 | `readiness` | Объяснить подтверждённый временной горизонт до следующего этапа работы с объектом. | статус дома, стадия строительства, заявленный срок сдачи | дата запуска аренды, ключи, доступность квартиры |
| 4 | `metro` / `transport_access` | Зафиксировать подтверждённый транспортно-географический профиль без вывода о спросе. | станция, время/способ пути, ж/д, шоссе, расстояние от МКАД | высокий арендный спрос, ликвидность, престиж, экономия времени без evidence |
| 5 | `daily_services` | Зафиксировать подтверждённые бытовые сервисы без портрета арендатора. | магазины, сервисы, ритейл, аптеки — только буквально | востребованность, «легко сдать», близость без evidence |
| 5 | `apartment_price` | Зафиксировать нижнюю границу покупки. | нижняя граница проекта, стартовая цена как ориентир | окупаемость, доходность, цена подходящего лота, попадание в бюджет |
| 6 | `location` | Зафиксировать географический профиль объекта. | район, город, направление | спрос арендаторов и престиж без evidence |
| 7 | `ads_count` | Зафиксировать текущий счётчик объявлений без рыночных выводов. | число объявлений на момент данных | спрос, конкуренция, скорость сдачи |
| 8 | `apartment_inventory` / `lot_examples` | Зафиксировать подтверждённое наличие форматов на момент свежего запроса. | буквальный inventory, доступные форматы, примеры лотов | будущая доступность, бронь, стабильный выбор |

Глобально запрещены: доход, ставка аренды, спрос, портрет арендатора, срок сдачи
в аренду, окупаемость и ликвидность без отдельных специализированных данных.

## 9. Overlay `financing`

Overlay применяется поверх `life / family / investment / rental`.

| Fact | `communication_goal` | `allowed_concepts` | `forbidden_meanings` |
|---|---|---|---|
| `mortgage_terms` | Зафиксировать только подтверждённые условия программы. | ставка, взнос, срок, название программы — только если они есть в свежем evidence | одобрение кредита, доступность программы сейчас, персональная ставка |
| `mortgage_rate` | Зафиксировать подтверждённую ставку отдельно от других условий. | ставка | одобрение, персональная ставка, ежемесячный платёж |
| `mortgage_down_payment` | Зафиксировать подтверждённый первоначальный взнос. | первоначальный взнос | персональные условия, одобрение, ежемесячный платёж |
| `mortgage_term` | Зафиксировать подтверждённый срок ипотеки. | срок | одобрение, персональные условия, ежемесячный платёж |
| `installment_months` | Зафиксировать подтверждённый срок рассрочки. | срок рассрочки | доступность без проверки, персональное право клиента |
| `discount` | Зафиксировать только подтверждённое условие скидки. | размер скидки, условие применения, источник подтверждения | гарантированное применение, срок действия без evidence |
| `payment_by_installments` | Зафиксировать подтверждённую схему рассрочки. | платежи, сроки, порядок оплаты — только если они есть в evidence | одобрение, доступность без проверки, персональное право клиента на рассрочку |
| `apartment_price` | Зафиксировать основу для расчёта, но не сам расчёт. | нижняя граница проекта или точная цена lot example | первый взнос/платёж без расчётного evidence, одобрение ипотеки |

Overlay не стирает основной `ScenarioAngle`. Он может добавить отдельный
финансовый блок или заменить CTA на проверку условий по выбранному ЖК.

### 9.1. Shortlist и selected scope

`presentation_scope="shortlist"` получает только `shared_facts`, нейтральные
`base_facts`, один сильный scenario anchor и необязательный financing overlay.
Lot/building/legal-поля в shortlist не передаются.

`presentation_scope="selected"` может дополнительно получить максимум пять
`detail_facts`. Точно запрошенный canonical fact поднимается первым, затем
применяется безопасный порядок:

| Detail fact | Допустимый смысл | Запрещённый вывод |
|---|---|---|
| `parking_price` | буквальная цена паркинга | место доступно, бронь, дефицит |
| `parking_inventory` | свежий буквальный счётчик | будущая доступность, гарантия места |
| `room_specific_price` | комнатность + соответствующая цена | лот есть сейчас, подходит по бюджету |
| `price_per_m2` | буквальная цена за м² | выгода, доходность, рост цены |
| `recurring_costs` | ставка/единица регулярного платежа | полная месячная стоимость владения |
| `purchase_terms` | trade-in, эскроу, 214-ФЗ как подтверждённые флаги | юридическая гарантия или персональная доступность |
| `building_profile` | этажность, лифт, тип, потолки | качество, надёжность, доступная среда без evidence |
| `property_formats` | подтверждённые типы объектов | текущий выбор или наличие в продаже |
| `lot_examples` | буквальные факты максимум из двух примеров лотов | наличие, бронь, перенос свойств на весь ЖК |

## 10. Правила композиции фасетов

1. Основной сценарий определяет **смысл** поля.
2. Facet определяет только **приоритет** поля.
3. Overlay `financing` добавляет отдельный набор подтверждённых финансовых
   данных и запретов.
4. Один факт нельзя одновременно использовать как общий факт и как уникальный
   benefit одной карточки.
5. Если один факт общий для всех карточек, он попадает в `shared_facts` один раз.
6. Для карточек выбираются разные anchors, если фактов достаточно.
7. Если безопасного уникального anchor нет, карточка остаётся короткой; код не
   создаёт искусственное преимущество.
8. В полезном первичном shortlist отсутствие части необязательных полей остаётся
   внутренней диагностикой и не превращается в общий `missing_note`. Клиентская
   оговорка нужна только когда пробел мешает ответить на конкретный выбранный
   объект, финансовый вопрос или запрошенный факт.

Пример:

```text
family + metro_access + financing

основной смысл:
  школы/сад/парк/двор → семейный распорядок
приоритет facet:
  metro поднимается выше readiness/finishing
наложение:
  mortgage_terms/discount добавляются отдельным блоком
```

## 11. Выбор акцента для трёх карточек

```text
available facts per card
   → убрать общие facts, уже вынесенные в shared_facts
   → упорядочить по приоритетам активного сценария
   → повысить приоритеты, заданные facet
   → выбрать первый неиспользованный безопасный fact
   → собрать ScenarioAngle из правила scenario × fact
```

Fallback-порядок:

1. уникальный факт из активного сценария;
2. уникальный нейтральный факт (`metro`, `location`, `readiness`, `finishing`,
   `area`, `property_class`, `developer`);
3. подтверждённое ценовое сравнение между карточками;
4. короткая фактическая карточка без выдуманной выгоды.

## 12. Что передавать модели

В `ResponseBrief`/`WritingPlan` передаётся только активный блок:

```json
{
  "scenario_context": {
    "primary_scenario": "family",
    "presentation_scope": "shortlist",
    "facets": ["metro_access"],
    "overlay": null,
    "shared_facts": [
      {"fact": "location", "evidence": "Москва"}
    ],
    "cards": [
      {
        "card_name": "ЖК …",
        "base_facts": [
          {"fact": "apartment_price", "evidence": [{"kind": "project_lower_bound", "value": 12000000}]}
        ],
        "anchor_fact": "schools",
        "evidence": ["школа", "детский сад"],
        "communication_goal": "объяснить роль подтверждённой инфраструктуры в семейной логистике",
        "allowed_concepts": ["школа", "детский сад", "семейный маршрут"],
        "forbidden_meanings": ["лучшая школа", "место гарантировано", "пять минут пешком"]
      }
    ]
  }
}
```

Правила других сценариев в запрос не включаются. Статический prompt объясняет
только, как превратить `scenario_context` в связный текст и JSON.
Для shortlist полные `OptionCard` не являются альтернативным источником прозы:
модель получает из них только точные имена и порядок. Нейтральные факты для
`facts` заранее выбираются кодом в `base_facts`, а описание строится только из
активного `anchor_fact` и необязательного `overlay_angle`.
Для selected scope подробности также приходят только через bounded
`detail_facts`, каждый со своим `communication_goal`, `allowed_concepts` и
`forbidden_meanings`.

## 13. Границы блокировки

До модели код обязан:

- нормализовать wire-поля;
- выбрать активный сценарий, facet и overlay;
- выбрать anchors и убрать дубли;
- сформировать evidence и смысловой коридор;
- не передавать неподтверждённые или несовместимые значения.

После модели код проверяет только механическую целостность: JSON/schema,
состав и порядок карточек, точный CTA и отсутствие неизвестных чисел/названий.
Редакторская семантика должна быть правильно подготовлена до вызова модели, а
не исправляться после генерации набором фразовых блокировок.

## 14. Оставшиеся известные расхождения

1. Текущие `allowed_benefit` в `scenario_recipes.py` всё ещё являются готовыми
   фразами для deterministic renderer. Offline model-facing payload уже удаляет
   их и использует `scenario_context`, но перед будущей унификацией renderer'ов
   старую prose-механику нужно либо заменить, либо явно оставить только в
   version-owned deterministic слое.
2. `refinement` сейчас выбирает общий `refined_shortlist` и может потерять
   механику покупательского сценария.
3. Историческая карта не содержит `rental` и `financing` и неверно считает
   `budget / metro_access / fast_move` самостоятельными сценариями.
4. Широкий поиск V0 запрашивает не все поля, которые умеет показывать его
   presentation layer.
5. Production Jivo использует deterministic renderer как fallback. `WritingPlan`
   может быть опубликован только через отдельный composer release gate в режиме
   `publish`; `shadow` оставляет клиентский текст deterministic, `off` выключает
   composer.
